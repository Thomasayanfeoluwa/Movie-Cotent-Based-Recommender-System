# Project State and Remediation Roadmap

## Purpose

This document records the repository review and staged remediation plan. The findings below describe the initial review; implementation status and verification are recorded in the progress log.

## Current state

The initial source review confirmed the following:

1. **Flask secret key has a known fallback.** `app.py` assigns `"dev-secret-key"` when `FLASK_SECRET_KEY` is missing.
2. **CSRF protection was not found.** Signup, signin, and review forms do not include CSRF tokens, and there is no CSRF middleware or dependency visible in the repository. Logout changes session state through GET.
3. **TMDB proxy rate limiting was missing at the initial review.** Rate limiting has since been added to the four TMDB proxy routes. Production storage is configured through `RATELIMIT_STORAGE_URI`; the project owner reports setting this to the Redis URL generated by Render. Do not store the URL or its credentials in this document or source control.
4. **`/recommend` returns exception text.** The route logs the exception and sends `str(e)` to the client with status 500.
5. **IMDb review scraping has no timeout.** The source review does not determine whether the scraping complies with IMDb's terms.
6. **README impact claims lack measurement evidence in the repository.** Claims include 10x faster recommendations, 40% fewer invalid searches, zero security incidents, 100% review submission success, and 3x faster page loads.
7. **No offline recommendation ranking evaluation was found.** The repository contains sentiment-classification metrics, but those do not evaluate recommender relevance. No relevance labels for recommender evaluation have yet been established.
8. **README demo URLs conflicted in the initial review.** The active Render app is now confirmed as `https://movie-recommender-mu4e.onrender.com/home`; its deployed feature set is behind the current worktree.
9. **README describes FAISS as approximate nearest-neighbor search, but the notebook builds `IndexFlatIP`, an exact flat index.**
10. **The sentiment-model selection claim should be revisited.** The checked-in notebook output shows Logistic Regression scoring higher than Linear SVM on the reported metrics, while the README says Linear SVM was the best-performing model.

The repository contains a Flask application, database models, and a TF-IDF/SVD/FAISS recommendation path. The source alone does not establish that the database is Neon or that the deployment is currently live.

## Proposed stages

### Stage 1 - Establish a baseline

- Add or identify focused tests for the routes and user flows that will be changed.
- Map all state-changing routes, including browser form and AJAX requests.
- Record which movie-discovery features must remain available to signed-out visitors.
- Inspect available deployment configuration for the demo URL and shared rate-limit storage.

**Acceptance checks**

- Existing key flows have tests or a documented verification procedure.
- Any intentional behavior changes are identified before implementation.
- Existing unrelated work is preserved.

### Stage 2 - Require a configured Flask secret

- Remove the known development fallback from `app.py`.
- Fail startup clearly when `FLASK_SECRET_KEY` is missing or blank.
- Document secure local and deployment configuration without adding a real secret to the repository.
- Add tests for missing, blank, and configured values.

**Acceptance checks**

- The application cannot start with a missing or blank secret key.
- A configured secret allows startup.
- No production secret is committed.

### Stage 3 - Protect state-changing requests against CSRF

- Add a Flask-compatible CSRF protection dependency and initialize it following the project's patterns.
- Add CSRF tokens to signup, signin, and review forms.
- Update AJAX submissions that issue state-changing requests so they send valid tokens.
- Change logout from GET to POST and protect it.
- Test that missing/invalid tokens are rejected and legitimate requests succeed.

**Acceptance checks**

- Every state-changing route is covered by CSRF protection.
- The normal signed-in and signed-out flows continue to work.
- Logout cannot be triggered by an unprotected GET request.

### Stage 4 - Limit TMDB proxy usage

- Keep anonymous movie discovery available unless product requirements say otherwise.
- Add request limits and sensible input bounds to the proxy endpoints.
- Prefer a shared rate-limit backend for multi-worker production. A per-process limiter must not be presented as reliable cross-worker protection.
- Configure `RATELIMIT_STORAGE_URI` with the Render Redis URL for shared production storage. Keep the URL secret and out of source control.
- Preserve the existing UI's access to search, movie, credits, and person data.
- Test normal requests, invalid/oversized inputs, and requests over the limit.

**Acceptance checks**

- Anonymous browsing continues to work within configured limits.
- Excessive proxy use is rejected predictably.
- The chosen storage backend and its deployment requirements are documented.

**Status: Complete.** The application requires `RATELIMIT_STORAGE_URI`, disables in-memory fallback, and applies one shared 120-requests-per-minute limit across the TMDB proxy routes. The project owner confirms that the Render-generated Redis URL is configured in the Render environment. The local rate-limit test uses `memory://` and verifies the shared route limit; it does not independently verify connectivity to the Render Redis instance.

### Stage 5 - Avoid returning internal exception details

- Keep diagnostic detail in server logs.
- Return a stable, generic error response from `/recommend`.
- Add a test that forces an exception and verifies internal exception text is not present in the response.

**Acceptance checks**

- The client gets a clear failure status/message without a traceback or exception details.
- The exception remains available in server logs for diagnosis.

### Stage 6 - Use application-submitted reviews

- Keep the review form and save signed-in users' reviews and sentiment labels in PostgreSQL.
- Do not fetch reviews from IMDb during recommendation-page rendering.
- Leave TMDB movie metadata, trailers, datasets, trained models, and recommendation behavior unchanged.
- Render recommendation pages whether or not a movie has saved user reviews.

**Acceptance checks**

- Recommendation pages do not make a live IMDb reviews request.
- Saved user-submitted reviews and their sentiment labels are displayed.
- Recommendation pages render an appropriate empty state when no reviews are saved.
- TMDB and recommendation behavior remain unaffected.

**Status: Complete.** IMDb review fetching has been removed from the runtime route; database-submitted reviews remain the review source. Tests verify saved reviews render, the no-reviews empty state renders, and no outbound HTTP request is made by either case.

### Stage 7 - Establish offline recommendation evaluation

- Use a blinded, prospective user-judgment study as the primary relevance source. Existing likes/dislikes are useful personalization signals, but the current history does not reliably capture which ranked items each user saw and judged.
- Collect a user's movie-preference profile and query, then generate top-12 lists from both the cold-start baseline and personalized recommender using the same profile/query case.
- Pool and deduplicate both lists, randomize the movie order, and have the user score each candidate for their stated taste: 0 = not relevant, 1 = somewhat relevant, 2 = highly relevant. Do not label unjudged or unseen movies as negative.
- Freeze the model and the 50/50 reranking weight before collecting the held-out judgments; do not tune against evaluation labels.
- Start with a pilot of at least 30 user/query-profile cases from at least 10 users, each with at least five prior explicit likes/dislikes. Use NDCG@10 as the primary metric and Precision@10 (relevant means score 2) as a secondary metric. Compare both systems on the same cases and report case count and uncertainty; report judgment coverage and do not claim catalog-wide recall from this pooled candidate set.
- Keep recommender evaluation separate from sentiment-classification evaluation.
- Correct the sentiment-model README claim to match the notebook evidence, or retrain/re-evaluate before making a different claim.

**Acceptance checks**

- Evaluation can be rerun and produces the documented metric outputs.
- The query/profile cases and relevance judgments are held out from tuning.
- Metrics are not claimed until their relevance labels and methodology are explained.

**Decision:** Use the user's explicit, blinded 0-2 relevance judgments for paired baseline-versus-personalized top-12 outputs. The current schema has explicit preferences and recommendation history, but does not provide robust per-item impression/rating labels for a valid historical offline benchmark. Do not treat missing feedback as dislike or report metrics until a held-out judgment set is collected.

### Stage 8 - Correct README claims and demo links

- Remove or qualify performance, reliability, security, and impact figures unless supporting measurements and methodology can be provided.
- Correct the FAISS description to reflect the exact flat index currently used, or update the description only if the implementation is deliberately changed and validated.
- Verify which Render URL is current and use one consistent URL in all README locations.
- If neither URL can be verified, label the demo as unverified rather than choosing one by assumption.
- Reconcile the claimed best-performing sentiment model with notebook results.

**Acceptance checks**

- README statements match implementation and checked-in evidence.
- Unsupported numerical claims are removed or accompanied by reproducible evidence.
- The demo is linked only to a verified destination, or clearly labeled unverified when none can be confirmed.

**Status: Complete.** Unsupported performance, reliability, security, and impact figures were removed or qualified. The README now describes the FAISS `IndexFlatIP` as exact search, distinguishes the LinearSVC artifact configuration from the notebook comparison where Logistic Regression scores slightly higher, and describes the current worktree's like/dislike personalization accurately. It documents `memory://` for local rate-limit testing and shared Redis configuration for production. The confirmed Render URL is linked; the README clearly notes that the currently deployed revision predates the local login and personalization changes.

### Stage 9 - Add a dedicated login page

- Provide sign-in and sign-up forms on `/login`.
- Require an authenticated session for movie pages, recommendation actions, and TMDB proxy endpoints.
- Keep static assets and `/health` publicly accessible.
- Redirect anonymous page requests to `/login` and return an authentication error for anonymous TMDB API requests.

**Acceptance checks**

- An anonymous visitor reaches the login page first and cannot access protected movie or TMDB routes.
- Valid sign-in creates a session and redirects to the movie home page.
- Both forms include CSRF tokens, and static assets and health checks remain reachable.

**Status: Complete.** The app now serves both forms on `/login`, gates movie/recommendation and TMDB routes, and retains public static assets and health checks. Tests cover login-page forms, successful sign-in, anonymous access denial, and authenticated discovery.

### Stage 10 - Refresh the movie discovery interface

- Add a responsive, streaming-service-inspired home layout using existing poster data and movie search.
- Keep recommendations, movie details, user feedback, and trailer playback on the existing routes.
- Present trailers as trailers; do not imply that the app streams full movies.

**Status: Implemented locally; regression and visual checks are pending.** The home page now has featured poster art, a search panel, and a horizontal movie rail. If TMDB is unavailable, the page falls back to movie titles from the local dataset with styled poster placeholders. Live TMDB search, posters, metadata, and trailers still require a valid `TMDB_API_KEY`; missing-key responses now explain this rather than showing a generic API alert. Movie cards use the existing movie-detail and recommendation flow when TMDB is configured.

### Stage 11 - Add content-based preference personalization

- Add explicit per-user like/dislike feedback keyed by stable TMDB movie ID; do not infer preference from review sentiment.
- Store the movie features needed to reuse the existing vectorizer and SVD transform.
- Rank candidate movies using both the searched movie and the user's saved content profile.
- Preserve the current ranking for users with no saved preferences and do not retrain the model.
- Add and apply a database migration for the feedback table.

**Acceptance checks**

- Signed-in users can save a like or dislike and change it for the same movie.
- Saved feedback is scoped to its user and uses the TMDB movie ID to prevent duplicate preferences for the same movie.
- Personalization changes ordering when feedback exists; cold-start ordering remains unchanged.
- Tests cover validation, persistence behavior, and ranking; TMDB failures do not save unusable feedback.

**Status: Complete.** Like/dislike controls save one preference per user and TMDB movie ID. The app creates a content profile from stored TMDB features and reranks up to 100 candidate titles with an even blend of query similarity and preference similarity. Users without feedback keep the existing ranking; the existing TF-IDF, SVD, and FAISS artifacts are reused. Migration `a6d271b2f3c4` adds the preference table and has been applied to the configured Neon database; other database environments still need the migration.

- Run focused tests for each changed stage and the repository's available broader checks.

- Record test results, deployment-only follow-up, and any remaining limitations here.

**Acceptance checks**

**Status: Complete for local verification.** The full test suite passes (21 tests), `git diff --check` passes, and a read-only review of the worktree found no significant issues. No Render deployment or Neon database operation was performed in this stage. Browser visual verification and production deployment remain separate follow-up work.

## Decisions to confirm before implementation

1. **Application access:** Sign-in is required before accessing movie discovery and recommendations. The login page and static assets remain public; the health check remains public for deployment monitoring.
2. **Reviews:** The runtime review source is application-submitted reviews stored in PostgreSQL; live IMDb review scraping is not used.
3. **Recommendation relevance data:** A meaningful ranking evaluation requires relevance judgments. The project owner must provide or approve the data and the assumptions used to label relevance.
4. **Demo URL:** `https://movie-recommender-mu4e.onrender.com/home` responds; its deployed revision currently does not include recent local changes.
5. **Personalization feedback:** Like/dislike was selected; review sentiment remains separate and is not treated as a preference.
